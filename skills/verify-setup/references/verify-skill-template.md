# Verify Skill Template

The file Step 4 writes to `.claude/skills/<name>/SKILL.md` and copies byte for byte to `.agents/skills/<name>/SKILL.md`. `<name>` is `verify` for a single app, `verify-<app>` for each app in a monorepo.

Fill every `<placeholder>` from Step 1 and Step 2. Each command keeps its source comment. Delete a section that does not apply (no build, no install), and say so in one line instead of leaving it empty. Never leave a placeholder in the written file.

## Template

````markdown
---
name: <name>
description: "Boot <app> and drive each feature in feature-map.md end to end, grading it PASS, FAIL or UNVERIFIED. Use before committing a change to <app>, or when asked to verify it. Don't use for unit tests."
---

# Verify <app>

Run this before you commit a change to <app>. It boots the app, drives every feature in `feature-map.md`, and grades each against the expected result there. Keep this folder identical to its copy in `<other copy path>`.

Generated by verify-setup from commit <base SHA>. Every command below cites the file it comes from; when that file changes, update the command here.

## Rules

- Run the commands exactly as written. Do not add retries, fixed sleeps or longer timeouts to make a step pass.
- Never edit `feature-map.md` to match what the app did. A failing row is reported; changing its expected result is the user's decision.
- Stop only the processes this run started. If the port is busy, report it and stop.
- Write logs only under `.verify/runs/` in this repo.
- Never print or copy secret values; only the variable names below.

## Prerequisites

- <runtime and version> (<source>)
- Environment variables, names only: <VAR> (<source>) — without it, rows <IDs> are UNVERIFIED.
- Driver: <browser tool | curl | built binary> — without it, rows <IDs> are UNVERIFIED.

## Steps

1. **Record the commit and set the environment.** `git rev-parse HEAD` and `git status --porcelain`; a dirty tree is verified as `dirty=yes`. Then export, in the same shell as every later step: <the environment block from verify-setup, only the lines this app's tools need>, so caches, logs and temp files stay under `.verify/`. Check the port is free.
2. **Install.** `<install command>`  <!-- source: <path:line> -->
3. **Build.** `<build command>`  <!-- source: <path:line> -->
4. **Boot.** `<boot command>`, in the background in its own process group (`setsid <boot command>` on Linux, `set -m` job control in bash elsewhere), its output to `.verify/runs/<UTC timestamp>/app.log`; keep the group's ID.  <!-- source: <path:line> -->
5. **Ready.** <ready check, e.g. poll `curl -fsS http://localhost:<port>/health` every second, up to <N> seconds>. This one bounded wait is the only loop allowed. Not ready in time: grade every row UNVERIFIED (boot failed), go to Teardown.  <!-- source: <path:line> -->
6. **Drive.** For each row of `feature-map.md`, in ID order, once: reach it, do the action, and compare what you observe with the expected result. A row marked as mutating runs only against <the local or test setup>; otherwise it is UNVERIFIED. Record `ID, status, observation, seconds` in `.verify/runs/<UTC timestamp>/results.tsv`.
   - PASS: the observation matches the expected result.
   - FAIL: it does not. Quote what you observed.
   - UNVERIFIED: the row could not run here (missing variable, driver or answer); say why.
7. **Teardown.** Stop the whole process group from step 4 and wait until the port is free, up to 10 seconds (still held: report a teardown failure) (and `<compose down command>` if this run started the stack), even after a failure.  <!-- source: <path:line> -->

For a CLI, steps 4, 5 and 7 are replaced by running each row's command and checking its exit code and output.

## Result

End with one line, exactly in this form, then one line per row that is not PASS:

```text
VERIFY <PASS|FAIL|PARTIAL> commit=<short SHA> dirty=<yes|no> pass=<n> fail=<n> unverified=<n> total=<n> seconds=<n>
F<id> <FAIL|UNVERIFIED>: <observation or reason>
```

- `PASS`: every row passed.
- `FAIL`: at least one row failed.
- `PARTIAL`: no row failed and at least one is UNVERIFIED.

A verdict holds only for the commit it names. After any change, run this skill again before claiming the change is verified.
````

## Notes for the generator

- The `<!-- source: … -->` comments are part of the generated file: they make every command traceable, and a reviewer can check them without running anything.
- The result line is fixed so other tools can read it: `ship` checks that a release commit is verified, and a reviewer can compare the `commit=` value with the commit under review. Keep its field names and order.
- Keep the generated skill short. It is read before every commit; the feature map carries the detail.
- When the repo has devops-pipeline's `scripts/e2e_test.sh`, the Drive step runs it as one row (see `references/detection.md` → *CLI smoke script reuse*).
